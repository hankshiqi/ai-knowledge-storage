# Milvus 切片入库优化说明

本文说明 `app/rag/import_/index_service.py` 中的入库保护逻辑，重点是让数据问题在删除旧数据之前暴露，并减少 schema 不匹配导致的 Milvus 运行时错误。

## 这次增加的保护

1. **客户端和集合配置检查**：Milvus 客户端不可用或 `CHUNKS_COLLECTION` 未配置时立即报出明确错误。
2. **已有集合 schema 检查**：导入前检查必需字段、字段类型、`chunk_id` 主键、自动生成主键配置、VARCHAR 长度和稠密向量维度。集合与当前导入格式不兼容时停止导入，提示迁移或重建集合。
3. **切片元数据补全**：缺少 `file_title` 时从流程状态补齐；每条切片的 `item_name` 统一使用状态中的识别结果；缺少 `parent_title` 时回退到 `title`；缺少 `part` 时设为 `0`。如果切片已有不同的 `file_title`，则报错，避免误删或混入其他文件的数据。
4. **删除前的数据校验**：检查必需字段、字符串类型、Milvus VARCHAR UTF-8 字节长度、`part` 整数类型、1024 维稠密向量、向量元素是否为有限数值，以及稀疏向量索引和值是否合法。
5. **过滤表达式转义**：删除旧切片时使用 JSON 字符串编码文件名，避免引号等特殊字符破坏 Milvus 过滤表达式。
6. **自动主键重跑处理**：向 Milvus 插入前从切片中移除旧的 `chunk_id`，避免重跑时将上一次自动生成的主键再次作为输入；插入后检查返回条数和 ID 数量，再回填主键。

## 对应的报错风险

- `item_name` 缺失：导入时统一从 state 补入每个切片，避免再次触发“Insert missed an field `item_name`”。
- 集合字段、类型或维度不一致：在插入前指出不兼容的字段，而不是等到 `insert` 阶段收到较难定位的 Milvus 异常。
- 字段超长或向量数据无效：在执行删除旧数据前校验，避免已删除旧数据后才发现新数据不符合 schema。
- 文件名包含引号：表达式中的字符串会被正确转义。
- 重复执行同一 state：不会把之前回填的自动主键当作下一次插入输入。

## 仍需注意

当前替换顺序仍然是**先按 `file_title` 删除旧数据，再插入新数据**。本地校验可以提前拦截格式错误，但如果删除成功后发生 Milvus 网络中断、服务端异常或插入失败，该文件的旧数据可能已经删除。并发处理同一个 `file_title` 也可能互相覆盖。要消除此类风险，需要将替换流程改成带版本标记的写入与切换，或先保存旧记录 ID、确认新记录插入成功后再删除旧记录；这会改变当前写入流程，尚未包含在本次优化中。

此外，实际 collection 的描述字段和服务端行为仍应在可连接 Milvus 的环境中验证；本地代码检查不能替代真实服务端集成验证。MongoDB 不属于本说明范围。
